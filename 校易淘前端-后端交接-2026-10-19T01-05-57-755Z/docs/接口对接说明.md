# 接口对接说明

本文区分已有文档约定与当前实现，不代表已冻结的完整 API 合同。路径来源为原需求文档，实际联调以双方确认的 OpenAPI 为准。

## 当前实现状态

| 内容 | 当前状态 |
| --- | --- |
| 商品、分类、购物车、订单页面 | 本地演示数据 |
| HTTP 请求层与以下业务 API 入口 | 已预留并可独立调用，尚未接入页面 |
| /api/v1/system/health | 原项目基础后端已实现，本次也验证代理；组员自己的后端需另行确认 |
| 正式密码登录、Token 刷新、上传、支付页面 | 未实现 |
| 库存、支付与售后规则 | 由后端实现，前端不能以本地结果代替 |

## 请求和响应规则

- 开发环境通过 Vite 代理；默认 /api/v1 → http://127.0.0.1:8080/api/v1，保留路径前缀。
- JSON 请求；认证请求携带 Authorization: Bearer <accessToken>。
- 当前请求层解包 data。调用方通过 try/catch 处理 ApiError 的 message、status、code、traceId。
- 规范响应暂按 {"code":200,"message":"success","data":{}}；分页 data 暂按 {"total":100,"page":1,"size":10,"list":[]}。
- 原文档成功码存在 200 与 100000 两种描述，请求层临时兼容两者；联调前应确定唯一值，不能长期让不同接口各用一套。
- 失败应返回对应 HTTP 状态及业务码，如 401、403、409；HTTP 200 但业务码失败也会抛错。
- 后端建议返回 X-Trace-Id 便于排查。直接跨域访问时还需暴露此响应头；同源代理访问无此额外限制。
- 不自动重试创建订单、支付或退款请求，避免在幂等约定不明时重复操作。
- 调用 setAccessToken(token) 后，认证接口才发送 Token。当前仅内存保存，刷新即丢失；刷新 Token 和登录态恢复方案需单独实现。
- 401 不会自动跳转或清除演示状态，接入真实页面时由认证模块统一处理。

## 已预留的接口入口

| 入口 | 方法与路径（省略 /api/v1） | 认证 | 对接要点 |
| --- | --- | --- | --- |
| systemApi.health | GET /system/health | 否 | 检查代理与应用存活 |
| authApi.login | POST /auth/login | 否 | 文档为 phone、password；不能使用昵称弹窗代替 |
| authApi.logout | POST /auth/logout | 是 | 成功或本地退出后 clearAccessToken |
| authApi.userInfo | GET /user/info | 是 | 服务端身份、昵称、角色 |
| productApi.list | GET /products | 否 | keyword、categoryId、school、sellerType、minPrice、maxPrice、condition、sort、page、size |
| productApi.detail | GET /products/{id} | 否 | 使用服务端商品 ID |
| productApi.categories | GET /categories | 否 | 类目树，不是本地分类字符串 |
| productApi.create | POST /products | 是 | title、categoryId、sellerType、price、stock、condition、description、images 等；图片上传与角色校验待接 |
| cartApi.list | GET /cart | 是 | 具体响应形状需确认，不能臆定为某个数组 |
| cartApi.add | POST /cart/items | 是 | productId、quantity |
| cartApi.update | PUT /cart/items/{id} | 是 | 数量字段和响应需确认；id 为购物车条目 ID |
| cartApi.remove | DELETE /cart/items/{id} | 是 | id 为条目 ID，不是商品 ID |
| orderApi.create | POST /orders | 是 | cartItemIds、addressId、deliveryType、remark |
| orderApi.list | GET /orders | 是 | 买家/卖家视角、状态和分页参数需确认 |
| orderApi.detail | GET /orders/{orderNo} | 是 | 返回订单明细和状态 |
| orderApi.cancel | PUT /orders/{orderNo}/cancel | 是 | 状态合法性由后端决定 |
| orderApi.confirm | PUT /orders/{orderNo}/confirm | 是 | 买家确认收货，不是前端直接标为完成 |
| paymentApi.create | POST /pay/create | 是 | orderNo、payMethod |
| paymentApi.status | GET /pay/{payNo}/status | 是 | 最终结果以后端为准，不以前端跳转为准 |

登录响应示例来自原文档：

    {"code":200,"data":{"token":"<access-token>","refreshToken":"<refresh-token>","expiresIn":7200,"user":{"id":"10001","nickname":"小李","role":1}}}

这里只说明响应形状，不包含可用 Token。Java Long 类型 ID 建议序列化为字符串，避免浏览器整数精度损失；最终由双方冻结。

下单请求示例：

    {"cartItemIds":["30001"],"addressId":"40001","deliveryType":1,"remark":""}

按卖家拆单的响应 data.orders 为数组。当前演示中“一次确认直接完成”的流程不能沿用到真实交易。

## 页面字段与后端字段映射

| 页面当前字段 | 正式对接方式 |
| --- | --- |
| p1、local-... 商品 ID | 替换为服务端 id；不得通过字符串截取转换 |
| books、digital 等分类 | 仅是 UI 示例分类；使用 categoryId 与后端类目表映射 |
| 本校、邻校 | 当前抽象筛选，实际 school/schoolId、当前用户学校需确认 |
| seller 字符串 | 后端需明确 sellerId、sellerNickname 或卖家摘要对象，前端做适配 |
| avatar 单个字 | 当前为昵称首字占位；真实头像 URL 字段需适配 |
| art、color | 只用于本地插画，真实商品应提供 images；需补商品图片组件 |
| time 分钟数 | 示例数据，正式改用 createTime / publishTime 等已确认时间字段计算 |
| condition 中文成色 | 需确认值为中文字符串还是枚举编码 |
| cart[].id | 演示中是商品 ID；真实购物车必须区分 cartItemId 和 productId |
| quantity 固定 1 | 当前演示仅单件二手商品，B2C 多库存数量编辑尚未实现 |
| 订单 no、status 文本 | 需适配 orderNo、服务端状态枚举，不能把演示完成作为支付成功 |
| 本地收货人/手机号/地址 | 正式使用地址管理接口的 addressId；快照与校验由后端负责 |
| 本地金额计算 | 仅展示；最终价格、佣金、配送费及库存由服务端重算 |
| 收藏列表 | 需求暂无接口，本次仍为本地功能；跨设备同步需要另议 |

## 联调前必须确认

1. 成功码、分页格式、ID 类型、时间格式与时区。
2. 商品和购物车响应字段的完整示例，商品图片 URL 访问方式。
3. 类目、学校、成色与角色枚举；真实用户可能多角色。
4. 地址管理接口、身份认证与审核接口；已有页面不能代替正式认证。
5. 下单幂等键的名字、放置位置和重放响应；现有请求层没有自行发送猜测的幂等 Header。
6. 多卖家拆单后的逐单/合并支付，以及过期订单的处理。
7. 取消、退款、售后、结算的状态机与接口错误码。
8. 发布页面尚无图片上传，文件接口字段名、大小限制、类型和审核需确认。
9. 生产前端域名、API 反向代理、HTTPS 和测试账号的交付方式。

## 接入顺序示例

先在 API 模块验证 productApi.list({ page: 1, size: 12 }) 的响应，再在 useMarketplace.js 将示例列表替换为请求结果并增加 loading/error/empty 状态。真实分页必须走后端，不能只筛选当前页假装全量搜索。

正式登录成功后，使用服务端返回的 token 调用 setAccessToken；再调用 userInfo 获取真实身份。不能拿演示 user.name 充当登录成功。

购物车、下单、发布应分别替换，不使用“接口失败就继续写 localStorage”的降级方式，以免用户误以为真实交易已经成功。
