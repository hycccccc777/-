# 风险登记表

> 用途：把「没做 / 做了一半」的事写清楚，而不是留白。
> 评审看到「未覆盖」会追问；看到「已评估、影响可接受、触发条件明确」通常就过了。
>
> 维护规则：每条都必须有 **触发条件**（什么时候必须回头看）。没有触发条件的条目视为没想清楚。

| 编号 | 项 | 当前状态 | 为什么不做（或做一半） | 影响 | 触发条件（何时必须补） | 缓解措施 | 负责人 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| R-01 | MySQL 主从 / 读写分离 | 单机单实例，`application-druid.yml` 里 `slave.enabled=false` | 当前数据量与 QPS（峰值 1354）远未到单机瓶颈；主从会引入复制延迟、故障切换与脑裂处理，收益不抵复杂度 | 数据库主机故障时全站不可用，RTO = 恢复耗时（实测从备份恢复约 3 分钟）；RPO = 最近一次备份（每日 02:00，最长 24 小时） | 日活 > 5000，或业务要求 RTO < 1 小时，或写入 QPS 持续 > 200 | 每日自动备份（计划任务）+ 异地副本 + `restore.ps1` 已做往返验证；备份恢复演练记录在 `docs/回滚演练记录.md` | 待定 |
| R-02 | 全链路追踪（Tempo/Jaeger） | 仅有 `traceId` 贯穿「网关 → 应用 → 日志」 | 单体应用内部无跨服务调用，span 的收益在拆服务后才体现；当前用 `traceId` + Loki 查询已能定位到「哪台机器、哪个接口、耗时多少」 | 无法看单次请求内部各阶段耗时分布（如「SQL 占了 80ms」需要看 Druid 慢 SQL 日志） | 出现第二个后端服务，或需要定位跨服务调用 | `ApiTraceFilter` 生成并透传 `X-Trace-Id`；Loki 里可按 traceId 串起访问日志 | 待定 |
| R-03 | 渗透测试 / 安全评估 | 未做第三方渗透 | 无预算；已按 OWASP Top 10 逐项自查并落到测试用例 | 可能存在未发现的业务逻辑漏洞（如价格篡改、越权边界遗漏） | 上线前或首次对外推广前 | 已有：SQL 注入（MyBatis 预编译）、XSS（XssFilter）、CSRF（无状态 JWT）、越权（按 buyer/seller 校验 + 越权 404）、限流（滑动窗口）、认证（JWT + 401 语义）。自查清单见 `docs/企业级能力对照表.md` 第四章 | 待定 |
| R-04 | Kubernetes / 服务网格 | 未使用，2 副本 + compose + Nginx | 4 个服务的规模上 K8s 是负资产：多一层运维、学习与调试成本，收益（弹性伸缩、自愈）在当前规模用不上 | 无自动弹性伸缩；扩容靠 `--scale`；节点故障恢复依赖 compose 重启策略 | 服务数 > 10，或需要按流量自动伸缩，或多租户隔离 | `docker-compose.scale.yml` 已支持多副本 + LB；健康检查就绪，迁 K8s 时可直接换编排层 | 待定 |
| R-05 | 消息队列 / 异步化 | 未引入 | 当前全部为同步短事务（下单 + 扣库存 + 写幂等 < 100ms），异步化会引入「消息丢失 / 重复消费 / 顺序」三个新问题 | 支付回调、通知类操作会阻塞请求线程；峰值时线程池可能打满 | 出现耗时 > 1s 的副作用操作，或需要削峰（如秒杀） | 幂等表已能承受重复投递，为将来引入 MQ 打好基础；限流已能挡住突发流量 | 待定 |
| R-06 | 静态检查（Checkstyle/ESLint） | 未接入 | 存量代码若全量开规则会产生数百条告警，修复成本高且与业务价值无关；时间优先给了可运行的正确性 | 代码风格靠 Code Review 约定，长期会腐化 | 团队 > 3 人或开始多人并行开发 | CI 已有「编译 + 39 用例 + 覆盖率门禁 + 依赖漏洞门禁」，能挡住功能性回归 | 待定 |
| R-07 | E2E 自动化（Playwright） | 未接入 | 前端只有 19 个单元用例，交互链路靠 compose 冒烟测试覆盖（起容器 → 打接口 → 校验数据） | 前端路由/组件级 bug 可能漏到线上 | 前端页面数 > 10，或改动频繁 | compose 冒烟测试覆盖主链路（登录 → 查商品 → 下单 → 支付）；`demo-business-loop.ps1` 可随时人工跑一遍 | 待定 |
| R-08 | 敏感字段统一脱敏 | 仅做到「日志不打印密码」 | 未做统一的 `@JsonSerialize` 脱敏层；当前手机号仅在管理后台展示，接口未对外暴露完整号码 | 若将来开放用户列表接口，可能批量泄露手机号 | 新增任何返回用户列表/详情的对外接口 | 日志侧已确认不打印密码；数据库账号口令改为环境变量注入 | 待定 |
| R-09 | 灰度发布的自动化判定 | 灰度分流与一键切回已实现，但「自动判断灰度是否健康」靠人看指标 | 自动判定需要历史基线（如「错误率比上周高 0.5% 就算异常」），当前没有足够历史数据 | 灰度期需要人工盯指标，反应速度取决于值班人 | 灰度常态化（每周多次） | Prometheus 已有 6 条告警规则；灰度期可临时加 `X-Canary-Cohort` 维度的错误率告警 | 待定 |
| R-10 | 密码策略 / 账号安全 | 密码 BCrypt 哈希，无复杂度强制、无登录失败锁定（仅限流） | 演示账号需要简单口令；生产应接入企业 SSO 或至少加强策略 | 弱口令账号可能被撞库 | 对外开放注册前 | 已有 IP 维度限流（10 次/60 秒）挡暴力破解；审计日志记录登录行为 | 待定 |
| R-11 | 容量规划与压测基线 | 有单机压测（1354 QPS / p95 56.8ms），无长期容量模型 | 缺少真实用户增长数据，无法做有意义的容量预测 | 扩容决策依赖经验判断 | 上线后 1 个月，拿到真实流量曲线 | 压测脚本 `scripts/loadtest.mjs` 可随时复跑；连接池 `maxActive=20` 是可调的第一杠杆 | 待定 |
| R-12 | 日志长期归档 | Loki 本地文件存储，保留 168 小时 | 归档到对象存储需要额外成本；7 天对排障足够 | 超过 7 天的历史日志不可查 | 合规要求或需要季度级回溯分析 | `docs/ops/loki-config.yml` 改 `retention_period` 与 `storage` 即可切换到 S3/OSS | 待定 |

## 一页版（给评审看的摘要）

| 类别 | 已完成 | 已评估不做（含触发条件） |
| --- | --- | --- |
| 高可用 | 多实例 + LB + 共享限流 + 定时任务集群 | MySQL 主从（R-01） |
| 可观测 | 指标 + 6 条告警 + Alertmanager 投递 + 日志集中化 | 全链路追踪（R-02）、日志归档（R-12） |
| 安全 | JWT / RBAC / XSS / CSRF / 越权 / 限流 / 依赖漏洞门禁 / 密钥环境变量化 | 渗透测试（R-03）、脱敏（R-08）、密码策略（R-10） |
| 发布 | 回滚演练（实测 ≤60s）+ 灰度（header / 比例 / 一键切回） | 灰度自动化判定（R-09） |
| 质量 | 39 + 19 用例、契约漂移校验、compose 冒烟 | 静态检查（R-06）、E2E（R-07） |
| 扩展性 | 单体分层 + 无状态 + 可水平扩容 | K8s（R-04）、MQ（R-05）、容量模型（R-11） |

**一句话**：所有「未做」都有理由、有影响说明、有触发条件；所有「已做」都有可当场执行验证的脚本或命令。
