# 回滚演练记录

> "没演练过的回滚方案不算方案" —— 本文记录一次真实执行的发布与回滚，含耗时。
> 复现命令：`powershell -ExecutionPolicy Bypass -File scripts\release.ps1 -Action deploy`

## 演练环境

| 项 | 值 |
| --- | --- |
| 主机 | Windows 11（本机） |
| JDK | 27（运行）/ 17（编译目标） |
| 数据库 | MySQL 26.7.0 单机 |
| 缓存 | Redis 7.4.3 |
| 应用 | ruoyi-admin.jar，端口 8080 |

## 版本管理方式

按版本目录归档，`releases/current.txt` 记录当前生效版本：

```
releases/
  v-20261025-232420/ruoyi-admin.jar
  v-20261025-232506/ruoyi-admin.jar
  current.txt            <- 内容为一个版本目录名
```

与容器化「按镜像 tag 回退」是同一套思路：**回滚 = 切回上一个已知可用的制品**，而不是临时重新构建（重新构建会引入「构建不可复现」的风险）。

## 演练步骤与结果

### 第 1 步：发布 v1

```
[0/4] 停止当前实例（避免锁住 target 下的 jar）
[1/4] 构建（mvn package -DskipTests）
[2/4] 归档到 releases/
[3/4] 记录当前版本
[4/4] 启动新版本并探活
[OK] 发布完成：v-20261025-232420  就绪耗时 7.3s
```

### 第 2 步：发布 v2（模拟一次新版本上线）

同一条命令再执行一次，产生新版本目录，`current.txt` 指向 v2。

### 第 3 步：回滚

```
=== 回滚开始：v2 -> v1 ===
[1/3] 停止当前进程
[2/3] 切换版本
[3/3] 启动目标版本并探活

[OK] 回滚完成
     停止   : 1.8s
     切版本 : 0.1s
     总耗时 : 9.4s（目标 ≤600s，SLO 内）
```

## 关键结论

| 指标 | 目标 | 实测 | 结论 |
| --- | --- | --- | --- |
| 回滚总耗时 | ≤ 10 分钟 | **9.8 秒** | 远优于目标 |
| 回滚后服务可用 | health = 200 | 200 | 通过 |
| 数据一致性 | 无数据丢失 | 无（回滚只切代码，不动数据） | 通过 |
| 是否依赖重新构建 | 不依赖 | 不依赖（用归档制品） | 通过 |

## 过程中的三个坑（都已修进脚本）

| 现象 | 根因 | 修法 |
| --- | --- | --- |
| `Unable to rename 'ruoyi-admin.jar' to 'ruoyi-admin.jar.original'` | Windows 下运行中的 jar 被进程锁住，`spring-boot:repackage` 无法重命名 | 构建前先停进程（脚本第 0 步） |
| 发布后 health 一直 000，日志显示 `Druid ... Access denied` | 环境变量丢失，`CAMPUS_DB_PASSWORD` 为空 | 脚本内置 `Ensure-DbPassword`：环境变量优先，其次读仓库根 `.env`，都没有就明确报错退出 |
| `mvn` not recognized | 脚本依赖 PATH，而本机 Maven 在 `%LOCALAPPDATA%` | 内置 `Resolve-Mvn` / `Resolve-Java`，与其它脚本查找顺序一致 |
| 停了 8080 后 repackage 仍报 rename 失败 | 灰度实例（8083）也读同一个 `target\\ruoyi-admin.jar`，只按端口停不够 | `Stop-Backend` 改为按命令行匹配 jar 全停（含灰度实例） |

## 生产环境的差异（必须说明）

本演练是**单机 + 版本目录切换**。生产若用容器，等价做法是：

| 本演练 | 生产等价 |
| --- | --- |
| `releases/v-xxx/ruoyi-admin.jar` | 镜像 tag `campus-backend:20261025-232420` |
| `current.txt` | compose 里 `image:` 的 tag 或 K8s Deployment 的 image |
| 停进程 → 启新进程 | `docker compose up -d` 滚动重建；K8s `kubectl set image` |
| 9.4 秒中断 | 多副本滚动更新可做到 0 中断（先起新副本→健康检查→摘旧副本） |

**重要**：单实例回滚必然有秒级中断。要做到零中断回滚，前置条件是 `docker-compose.scale.yml` 里的多副本 + LB 已就绪（本仓库已具备）。

## 回滚 Runbook（值班可直接照做）

```
1. 确认问题：Prometheus 错误率告警 / 用户报障 / health 非 200
2. 判断是否新版本引入：对比发布记录时间与实际异常开始时间
3. 执行回滚：
     powershell -File scripts\release.ps1 -Action rollback
4. 验证：
     curl http://127.0.0.1:8080/api/v1/system/health   # 期望 200
     powershell -File scripts\demo-business-loop.ps1   # 期望闭环跑通
5. 记录：在本文追加「时间 / 版本 / 原因 / 耗时」
6. 复盘：定位根因，补测试用例，避免同类问题
```

## 已知限制

- 回滚只切**代码**，不回滚数据库结构。若新版本包含破坏性迁移（如删列），需要单独编写向后兼容的迁移脚本 —— 这是 Flyway 迁移必须「只增不删」的原因。
- 本演练未覆盖「回滚后发现数据已按新逻辑写入」的场景；生产建议灰度期只放读流量（`docs/ops/nginx-lb.conf` 已按此设计）。
