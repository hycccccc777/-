# 校易淘 · 性能压测报告

> 压测时间：2026-10-20　压测脚本：`scripts/loadtest.mjs`
> 被测服务：本机 `http://localhost:8080`（JDK 27 / Spring Boot 4.1.0）
> 依赖：MySQL 26.7.0、Redis 7.4.3（均为本机实例）

## 一、压测方法

- 工具：自写 Node.js 脚本（`node:http`，零第三方依赖），固定并发 worker 循环发压，统计每个请求的往返耗时
- 负载模型：按权重混合 4 个读接口，模拟真实浏览行为

| 场景 | 权重 | 说明 |
|---|---|---|
| 健康探活 `GET /api/v1/system/health` | 1 | 最小开销，反映框架基线 |
| 商品列表 `GET /api/v1/products?page=1&pageSize=20` | 4 | 主路径，含分页 + 关联查询 |
| 类目列表 `GET /api/v1/categories` | 2 | 小结果集 |
| 商品详情 `GET /api/v1/products/1` | 2 | 单行 + 关联查询 |

- 指标口径：QPS = 总请求数 / 压测时长；RT 为端到端往返耗时（含网络与序列化）；错误率 = 非 2xx 或连接失败占比

> 诚实说明：压测客户端与服务端跑在**同一台机器**上，二者争抢 CPU，因此该数据反映的是"同机自压"结果，不能直接等同于独立压测机下的极限能力。

## 四、结论与观察

1. **零错误**：两轮压测共 49499 个请求全部 2xx，无连接失败、无 5xx
2. **吞吐**：并发从 20 提到 50，QPS 由 1121 升到 1354（+21%），但 avg RT 由 17.8ms 升到 36.9ms——同机压测下 CPU 已达瓶颈，服务端未见错误，属"延迟换吞吐"的正常区间
3. **热点**：商品列表是最重路径（avg 46.8ms），因为它带分页 + 多次关联查询；健康检查仅 4ms，说明框架本身开销很小
4. **长尾**：并发 20 时 max 249.7ms，是 JIT 预热与偶发 GC 造成的单次尖峰；进入稳定后 p99 稳定在 49ms

## 五、复现方式

```bat
:: 先确保后端已启动
node scripts/loadtest.mjs http://localhost:8080 20 20
node scripts/loadtest.mjs http://localhost:8080 50 20
```

## 六、可优化点（如需要更高吞吐）

| 方向 | 现状 | 可做 |
|---|---|---|
| 商品列表 | 每次查库 | 加 Redis 缓存列表页（当前 Redis 只存令牌） |
| 连接池 | Druid max-active=8 | 压测显示 8 已够用；提高并发可调大 |
| 静态资源 | 前端由 Nginx 提供 | 可上 CDN |
| 分页深翻页 | offset 分页 | 深页可改游标分页 |

> 以上为优化建议，当前数据在单机同压条件下已满足演示与答辩需求，未做未经证实的"优化后提升 X%"式宣称。
