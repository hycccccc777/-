# 答辩问答稿

> 10 个最可能被问到的问题。每个答案的结构：**先给结论 → 再说理由 → 再指证据 → 最后讲边界**。
> 所有数字与代码位置都来自本仓库实测，被追问时可以直接打开文件指给对方看。

## Q1　为什么不做微服务？单体怎么保证可扩展？

**结论：** 现阶段拆微服务是负收益，因为交易、库存、支付共享一个数据库，拆开就要处理分布式事务。

**理由：**
- 系统的核心一致性需求是「下单 = 建订单 + 扣库存 + 写幂等记录」，这在单库里是一个本地事务，一条 `@Transactional` 就保证。
- 一旦拆成订单服务 + 库存服务，这三步就变成跨服务调用，必须上 Saga 或 TCC，复杂度指数上升，而流量根本还没到需要拆分的量级。
- 可扩展性我放在了两个真正会先出问题的地方：**限流器支持 Redis 共享计数**（多副本不再失效）、**无状态 JWT**（会话不绑实例，可直接水平扩容）。

**证据：** `CtOrderServiceImpl:120,327` 的事务边界；`SlidingWindowLimiter` 的 memory/redis 双实现；`application.yml` 里 `campus.ratelimit.store`。

**边界：** 如果日订单到十万级、或要独立扩缩不同域，那时先拆「支付回调 + 通知」这类异步链路，而不是先拆核心交易。

## Q2　库存怎么防超卖？为什么不用 version 乐观锁？

**结论：** 用**条件原子扣减**，把判断和扣减压进同一条 SQL，交给数据库的行锁保证，不需要应用层读改写。

**理由：** version 乐观锁要先 `select` 出 version、再 `update ... where version = ?`，是两次往返，且失败要重试；而 `update ... set stock = stock - ? where stock >= ?` 一条语句就完成「检查够不够 + 扣减」，`affectedRows = 0` 即代表库存不足。更少的往返、更简单的失败语义。

**一个坑我踩过并写进了注释：** MySQL 的 SET 是从左到右求值的。如果先写 `stock = stock - qty`，后面的售罄判断读到的就是**已扣减后**的值，剩 1 件时会被误判成售罄。所以判断必须放在前面。

**证据：** `CtProductMapper.xml` 的 `deductStock`（含那段注释）；`StockConcurrencyTest` 用库存为 1 的商品并发下单，验证只有一单成功。

**边界：** 这套机制依赖单库行锁。若做分库分表，同一商品的库存必须路由到同一分片，否则要换成分段库存 + 分布式锁。

## Q3　幂等是怎么做的？为什么幂等表要和订单表分开？

**结论：** 客户端带 `idempotencyKey`，服务端靠 **`ct_idempotency` 表上的唯一键**挡住重复请求，重复提交返回同一 `groupNo`。

**理由：** 靠「先查订单表看有没有」是不安全的——两个并发请求会同时查到「没有」，然后各写一张单。唯一键是数据库层裁决，天然互斥。分开建表的原因是**幂等键的语义比订单更长**：一次请求可能产生多张订单（多卖家拆单），也可能什么都没产生（校验失败），用一个独立表记录「这次请求已经处理过」最干净。

**证据：** `uk_ct_idem_key` 唯一索引；`ApiOrderController:37-50` 支持请求体 `idempotencyKey` 或 `Idempotency-Key` 头；`IdempotencyConcurrencyTest` 并发验证只落一单；业务闭环演示里连点两次返回同一 groupNo。

**边界：** 幂等键需要客户端生成并保证重试时复用；如果是纯服务端生成，就退化成「无法防重放」。

## Q4　多卖家拆单，一个卖家成功一个失败怎么办？

**结论：** 拆单、库存扣减、幂等记录**在同一个事务里**，任一失败整体回滚，不会出现「一半成功」。

**理由：** 拆单的产物是同 `group_no` 下的多张订单，用 `uk_ct_order_group_seller` 保证同组同卖家唯一。因为都在一个库、一个事务里，不存在部分提交。真正的分布式场景（跨库/跨服务）才需要 Saga 补偿。

**证据：** `uk_ct_order_group_seller` 唯一索引；`CtOrderServiceImpl` 的事务方法；`OrderLifecycleTest` 覆盖全链路。

**边界：** 如果将来把「支付」独立出去，支付成功但订单创建失败就会成为真问题，那时需要本地消息表 + 补偿任务。

## Q5　限流为什么用滑动窗口？多实例为什么必须 Redis？Redis 挂了怎么办？

**结论：** 滑动窗口是因为固定窗口有临界点双倍流量问题；多实例必须 Redis 因为进程内计数会被放大 N 倍；Redis 挂了**放行**并告警。

**理由：**
- 固定窗口：限 60/分钟，用户在 59 秒和 61 秒各发 30 个，跨窗口合计 60 个，边界瞬间打穿。
- 进程内计数：2 个副本 = 每个各算 60，实际放行 120，限流形同虚设。这是**功能性失效**，不是性能问题。
- 故障策略选 fail-open：限流是保护手段，不该因为缓存抖动把整个业务打死。失败留 WARN 日志，靠告警发现。

**证据：** `SlidingWindowLimiter` 的 Lua 脚本（`ZREMRANGEBYSCORE` → `ZCARD` → `ZADD` → `PEXPIRE` 四步原子）；`RedisSharedRateLimitTest` 两个实例共享配额 + 内存对照组证明「不共享就会翻倍」；实测交替请求第 11 次起两个实例同时 429。

**边界：** fail-open 意味着 Redis 长时间不可用时没有限流保护，需要配合网关层限流或熔断兜底。

## Q6　「认证失败返回 HTTP 200」这个 bug 是怎么发现的？为什么之前一直没发现？

**结论：** 是写角色权限演示脚本时，用 `curl` 看状态码发现的——body 里写着 `code:401`，HTTP 却是 200。

**为什么之前没发现：** 因为前端只读 body 里的 `code` 字段判断业务成功与否，401 和 200 在 UI 上表现一样（都进错误提示），功能测试全过。而单元测试里断言的是 `e.getCode() == 401`（业务码），也没覆盖 HTTP 状态。

**危害（这才是重点）：**
- 网关 / CDN / 监控全按 HTTP 状态判成败 → 未登录被统计成成功请求，错误率指标永远正常。
- 前端 `shouldRefresh` 的判断是 `error.status === 401` → **令牌刷新分支永远不会触发**，用户只能被动登出。

**根因：** 若依框架的 `ServletUtils.renderString` 里写死了 `setStatus(200)`，所有走它的认证失败都受影响。

**修复：** 新增带状态码的重载 `renderString(response, body, status)`，认证失败传 401，越权按 404（不泄露资源是否存在）。

**证据：** `ServletUtils.java` 的重载；`AuthenticationEntryPointImpl` 改为传 `SC_UNAUTHORIZED`；实测匿名 `GET /api/v1/orders` 现在返回 401。

## Q7　覆盖率只有 43%，是不是说明测试不够？

**结论：** 43% 是按**全部 73 个业务类**算的；核心交易路径（订单、库存、幂等、支付、状态机）覆盖率远高于此，拉低整体的是 DTO、实体、`getter/setter` 和若依生成的通用 CRUD。

**理由：** `CtOrderServiceImpl` 行覆盖 85.7%，`CtProduct` 54.2%。而未覆盖行数最多的是 `CtProductServiceImpl`（95 行）、`CtUserProfile`（43 行，纯 POJO）、`CtAddress`（39 行）、`CtSchool`（36 行）——后三个基本是实体类。

**我做了什么而不是只解释：**
- CI 加了 35% 门禁，低于就红，防「用例越加越水」。
- 门禁失败时会**列出未覆盖行最多的 10 个类**，指哪补哪，而不是干瞪眼。

**证据：** `docs/screenshots/10-coverage.png`；`scripts/check-coverage.ps1`；门禁正反两向实测（43.2% 通过 / 阈值 60% 失败并输出清单）。

**边界：** 43% 对「能上线」这个标准偏低，但对「核心逻辑有并发与边界验证」是够用的。要提到 70% 需要补 Controller 层与参数校验分支的用例。

## Q8　压测 1354 QPS 是同机自压，怎么证明真实能力？瓶颈在哪？

**结论：** 同机自压的数字只能说明「不会因为代码问题先崩」，不能说明极限容量。瓶颈在同机 CPU 争抢，不在应用本身。

**理由与观察：**
- 并发 20 → 50，QPS 只从 1121 涨到 1354（+21%），但 avg RT 从 17.8ms 涨到 36.9ms。**吞吐涨幅远小于延迟涨幅**，是典型的「服务端已饱和」信号。
- 健康检查只要 4ms，说明框架与容器开销很小；商品列表 46.8ms 是最重路径（分页 + 多次关联查询）。
- 两轮 49499 个请求零错误、零 5xx，说明饱和时是排队而不是报错，这是好现象。

**证据：** `docs/性能压测报告.md`；`scripts/loadtest.mjs`（可复现）。

**边界：** 要拿到真实容量，需要独立压测机 + 调大连接池（`max-active: 8` 其实很可能也是瓶颈之一）。我没做，也不宣称。

## Q9　现在离企业级上线还差什么？给你两周先做什么？

**结论：** 业务代码和工程习惯够用，差的是「生产运行时」那一层。

**两周的优先级：**
1. **多实例 + 负载均衡 + 定时任务去重**（Quartz 默认 RAMJobStore，多实例会重复执行）
2. **日志集中化**（Loki/ELK）+ **告警通道打通**（现在只有规则，没有接收端）
3. **灰度与回滚演练**（10 分钟内完成回滚，写进 runbook）
4. **静态检查与 E2E**（Checkstyle/ESLint + Playwright 主链路）

**先不做的：** 消息队列、分布式事务、CDN。没有真实异步需求就上 MQ，只会多一个要运维的故障点。

**证据：** `docs/企业级能力对照表.md` 的「未覆盖项汇总」表，每一项都写了原因和最小改动方案。

## Q10　AI 用到什么程度？怎么保证 AI 写的代码是对的？

**结论：** AI 用在骨架生成、测试补全、排障推理和文档整理；**每个结论都必须落到一次可复现的实验上**才算数。

**具体把关方式：**
- 生成代码：分层边界、事务范围、SQL 写法逐个人工复核，不接受「能跑就行」。
- 生成测试：断言必须来自业务规则（比如「第 6 次必须拒绝」「库存不能变负」），而不是复述实现。
- 排障：本次三个问题——JaCoCo 覆盖率恒为 0、mysqldump 恢复失败、认证返回 200——**都是先怀疑结论、再做对照实验定位的**。比如覆盖率那个，把输出路径改到纯英文目录 `C:\jacoco-test`，文件立刻产出，才确认是中文路径导致的 agent 失败。
- 文档：所有数字必须来自本机实际执行，没有实测的一律不写，或者明确标注「未覆盖」。

**边界：** AI 会给看起来很合理的错误答案（例如「加个 `@Transactional` 就好了」）。判断标准只有一条：**能不能用一次实验证伪它**。
